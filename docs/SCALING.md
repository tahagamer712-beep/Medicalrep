# SCALING.md — حدود SQLite وخطة الانتقال

## ما أثبتناه فعلًا (وما لم نثبته)

**أثبتنا** باختبارات آلية (`test_concurrency.py`):
- 200 كتابة متزامنة (10 خيوط × 20) على نفس ملف المكتب: لا ضياع، لا أخطاء.
- القرّاء لا يُحجبون أثناء الكتابة (WAL).

**لم نثبت** — وهذا مهم:
- اختبار 200 كتابة **ليس** دليلًا على ملاءمة الإنتاج. كان على جهاز واحد،
  بعمليات صغيرة، دون زمن استجابة مُقاس، ودون حمل حقيقي متزامن من شبكة.
- لم نختبر: مئات المستخدمين المتزامنين، ملفات >1GB، نسخًا احتياطيًا أثناء
  ذروة الكتابة، أو تعافيًا من انقطاع كهرباء أثناء معاملة.

## حدود SQLite الموثقة لهذا النظام

| الحد | التفصيل |
|---|---|
| كاتب واحد لحظيًا | WAL يسمح بقارئين + كاتب، لكن الكتّاب يتسلسلون (busy_timeout=5s ينتظر بدل الفشل) |
| لا وصول شبكي | الملف محلي فقط — لا مشاركة بين أجهزة |
| DDL غير ذرّي عبر pysqlite | COMMIT ضمني قبل DDL (مُثبت) — ترقياتنا ذرّية على مستوى الملف |
| اتصالات WAL المتسربة | `pop` دون `dispose` = ‎"disk I/O error"‎ للاتصالات الجديدة (R7) |
| حجم عملي | مريح حتى ~1-2GB لكل ملف مكتب؛ بعده الترقية إلزامية |

## متى ننتقل إلى PostgreSQL (معايير قرار، لا تخمين)

1. فشل `test_concurrency` بعد رفع الحمل (50 خيطًا × 100 كتابة).
2. تجاوز أي ملف مكتب 2GB.
3. طلب تقارير لحظية عابرة للمكاتب (JOIN عبر ملفات مستحيل).
4. حاجة وصول شبكي متعدد الأجهزة لقاعدة واحدة.

## خطة الانتقال (مصممة مسبقًا، لا تُنفَّذ الآن)

- طبقة Repository/Service تعزل SQL — التغيير في `manager.py` + `repositories.py` فقط.
- Alembic جاهز للهوية المركزية (`alembic/` موجود ويُختبر).
- قواعد المكاتب: خياران — (أ) قاعدة PostgreSQL واحدة مع schema لكل مكتب،
  (ب) قاعدة لكل مكتب. القرار عند الحاجة بناءً على العزل المطلوب.
- ترحيل البيانات: تصدير SQLite ← استيراد PostgreSQL عبر طبقة Repository
  (لا SQL يدوي)، ثم تشغيل نفس حزمة الاختبارات ضد PostgreSQL.
- تقدير: 2-4 أسابيع عمل عند تحقق أحد المعايير أعلاه — لا يُبدأ قبلها.
