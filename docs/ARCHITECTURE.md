# ARCHITECTURE.md — بنية النظام

## 1. نظرة عامة

نظام متعدد الشركات والمكاتب لإدارة المندوبين الطبيين، يُدار بالكامل من الهاتف.
يتكوّن من ثلاث طبقات:

```
┌─────────────────────────────────────────────────┐
│  الواجهات: بوت Telegram (Owner) — لاحقًا WhatsApp │
├─────────────────────────────────────────────────┤
│  الخدمات: FastAPI + طبقة Service/Repository      │
├─────────────────────────────────────────────────┤
│  البيانات: قاعدة هوية مركزية + ملف SQLite لكل مكتب│
└─────────────────────────────────────────────────┘
```

## 2. المكوّنات

| المكوّن | التقنية | الدور |
|---|---|---|
| `app/main.py` | FastAPI | نقطة دخول الخادم + Webhooks (مستقبلًا) |
| `app/core/` | Python | إعدادات، أمان، صلاحيات، وقت، idempotency |
| `app/identity/` | SQLAlchemy | الهوية المركزية: شركات/مكاتب/مستخدمون/عضويات |
| `app/databases/` | SQLAlchemy | سجل قواعد المكاتب + مدير المستأجرين (tenant) |
| `app/services/` | Python | منطق العمل: مندوبون/خطط/زيارات/رواتب/تقارير |
| `app/telegram_owner/` | python-telegram-bot v21 | بوت الـ Owner |
| `app/jobs/` | APScheduler | تذكيرات وتقارير ونسخ احتياطية |
| `app/exports/` | openpyxl | تصدير Excel/CSV/PDF |

## 3. نموذج العزل (الأهم)

- **قاعدة الهوية المركزية** (`data/identity.db`): شركات، مكاتب، مستخدمون، عضويات
  (user ↔ office ↔ role)، مراجع قواعد المكاتب، حالة الخدمات، سجل تدقيق مركزي.
  **لا** تحتوي رواتب أو زيارات أو خططًا تفصيلية.
- **قاعدة كل مكتب** (`data/office_{office_id}.db`): كل البيانات التشغيلية للمكتب.
- **القاعدة الذهبية:** الخادم يحدّد قاعدة البيانات من **هوية المستخدم وعضويته**،
  أبدًا من نص يرسله المستخدم. لا استعلامات عابرة للمكاتب إلا عبر مسار Owner
  موثّق يُنفَّذ مكتبًا-مكتبًا مع تدقيق.
- الاستعلام الخاطئ **مستحيل** أن يسرّب بيانات مكتب آخر لأن الاتصال بقاعدة
  مختلفة أصلًا، وليس مجرد `WHERE office_id = ...`.

## 4. طبقة Repository/Service (للترحيل إلى PostgreSQL)

```
Telegram handler → Service (قواعد العمل) → Repository (SQLAlchemy) → SQLite
```

- الـ Repository يعزل كل SQL؛ الـ Service لا يعرف نوع قاعدة البيانات.
- الترحيل إلى PostgreSQL = تغيير `DATABASE_URL` + تشغيل Alembic. لا تغيير في
  منطق العمل.

## 5. قرارات تقنية (ADR)

| # | القرار | السبب |
|---|---|---|
| 1 | SQLite ملف لكل مكتب (بداية) | يعمل بثبات على Termux؛ العزل فيزيائي؛ الترحيل سهل |
| 2 | SQLAlchemy 2 sync (بدون async في DB) | أبسط للتصحيح على الهاتف؛ البوت async والـ DB sync عبر sessions قصيرة |
| 3 | WAL mode لـ SQLite | يسمح بقارئين مع كاتب واحد دون قفل كامل |
| 4 | Fernet لكل مكتب للنسخ الاحتياطية | مفتاح مستقل لكل مكتب، مخزّن خارج النسخة |
| 5 | تخزين UTC وعرض بتوقيت المكتب | كل مكتب له `timezone` قابل للتغيير (افتراضي Asia/Baghdad) |
| 6 | APScheduler مع جدول `job_runs` | منع تكرار المهام بعد إعادة التشغيل (idempotency في DB لا الذاكرة) |
| 7 | لا Docker على Termux | يُعقّد الهاتف؛ التشغيل مباشر بـ Python |

## 6. حدود SQLite الموثقة (ليست خيارًا نهائيًا تلقائيًا)

- كاتب واحد في اللحظة (WAL يخفف لكن لا يلغي).
- لا وصول شبكي — القاعدة ملف محلي فقط.
- مناسبة لمكتب واحد بعشرات المستخدمين المتزامنين؛ **غير مناسبة** لمئات الكتّاب
  المتزامنين أو عندما تصبح الحاجة لتحليلات عابرة للمكاتب لحظية.
- معيار الترحيل إلى PostgreSQL: عندما يفشل اختبار التزامن أو يتجاوز حجم
  قاعدة المكتب ~2GB أو تُطلب تقارير لحظية عابرة للمكاتب.
